# ADR-0003: PostgreSQL як основа: Timescale для історії цін, pgvector для RAG

**Статус:** прийнято · 2026-07-11

## Контекст

Потрібні: реляційне ядро (каталог, офери, акаунти, лінки), time-series історія цін (~сотні мільйонів
точок/рік), векторний пошук для RAG-матчингу і семантичного пошуку, кеш, сховище сирих payload'ів.

## Рішення

Один клас СУБД — **PostgreSQL 16** (образ `timescale/timescaledb-ha`, містить TimescaleDB і pgvector):

- Реляційне ядро: schema-per-service, ULID PK, JSONB для атрибутів, ltree для категорій.
- **TimescaleDB**: hypertable `price_points`, compression >90д, continuous aggregates (daily min/avg/max/last).
- **pgvector**: ембединги товарів, HNSW індекс; гібридний пошук = FTS + vector + RRF в одному SQL.
- **Redis** — кеш і rate-limit стан (ephemeral). **S3/MinIO** — raw payloads і зображення.

## Альтернативи

- *ClickHouse для цін*: сильніший на масовій аналітиці, але друга СУБД в експлуатацію на старті не виправдана;
  Timescale покриває наші обсяги (розрахунок в ARCHITECTURE.md §8). Міграція можлива пізніше — джерело подій збережене.
- *Qdrant/Weaviate для векторів*: виграш з'являється на >10M векторів або складному фільтруванні;
  у нас одиниці мільйонів — pgvector достатньо, мінус одна система. Інтерфейс `VectorIndex` у search-service
  абстрагує заміну.
- *MongoDB для каталогу*: JSONB у Postgres дає те саме + транзакції + єдина СУБД.

## Наслідки

- Експлуатуємо один клас БД — простіші бекапи, моніторинг, найм.
- Точка перегляду: >5 постачальників-мільйонників або вимоги реалтайм-аналітики по цінах → винести
  price-history у ClickHouse (append-only події це дозволяють без болю).
