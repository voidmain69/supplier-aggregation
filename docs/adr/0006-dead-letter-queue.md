# ADR-0006: Dead-letter queue — обмежені ретраї + `sa.dlq.<topic>` + реплей

**Статус:** прийнято · 2026-07-12

## Контекст

Консюмери комітять офсет тільки після успіху (at-least-once, ідемпотентні хендлери — hard rule 3).
Але handler, що падає постійно (баг, «отруєне» повідомлення, недоступна залежність), раніше пробрасував
виняток без коміту — одне повідомлення переставлялося нескінченно й **блокувало партицію** для всіх
наступних. Потрібен запобіжник, який не жертвує at-least-once і не втрачає дані.

## Рішення

Логіка живе в одному місці — `KafkaEventConsumer` (`libs/messaging`), тож усі консюмери отримують її
безкоштовно:

1. **Обмежені ретраї з backoff** — 1s / 10s / 60s (конфіг; `sleep` інжектується для тестів).
2. Після вичерпання — повідомлення йде **verbatim** у `sa.dlq.<topic>` через інжектований `DeadLetterSink`
   (структурно задовольняється `KafkaPublisher.send_raw`), зберігаючи оригінальні payload + headers і
   додаючи `x-failure-reason`, `x-attempts`, `x-original-topic`. Потім офсет **комітиться** — партиція
   рухається далі.
3. Без DLQ-sink поведінка — re-raise (fail-loud за замовчуванням): партиція стоїть, чекає людину.
4. Реплей — `tools/replay_dlq.py`: дренаж DLQ-топіка → перепублікація у вихідний топік (з headers), коміт
   лише після успіху.

Схема DLQ і backoff-розклад зафіксовані в `docs/standards/events.md §4/§5`.

## Альтернативи

- *Нескінченний ретрай на місці* — статус-кво; один poison блокує партицію. Відкинуто.
- *Пропустити (skip) і комітити без DLQ* — тиха втрата даних; неприйнятно для цінових подій.
- *DLQ у кожному сервісі окремо* — дублювання і розсинхрон; логіка в спільному консюмері краща.
- *Wrap payload у JSON-конверт для DLQ* — ускладнює реплей; verbatim-байти + Kafka-headers чистіші.

## Наслідки

- Poison-повідомлення більше не блокує партицію; деградація локалізована до одного офера/події.
- Метрика `dlq_messages_total` (labels topic/type/service) належить рівню observability-обгортки
  (там є `service`-контекст); алерт «DLQ > 0 за 15 хв» працює і з глибини DLQ-топіка.
- Backoff у 60s подовжує «хвіст» обробки збійного повідомлення — прийнятно, бо це рідкісний шлях;
  для гарячих топіків розклад — конфіг.
