# ADR-0001: Монорепо, Python 3.12, uv workspace

**Статус:** прийнято · 2026-07-11

## Контекст

Платформа з ~9 сервісів та 4 бібліотек, команда невелика, контракти (події, DTO) спільні та часто змінюються
на старті. Існуючий суміжний сервіс компанії (getAttrService: semantic matching, нормалізація атрибутів) — Python.

## Рішення

1. **Монорепо** з uv workspace: `libs/*` + `services/*` + `apps/*` в одному репозиторії.
2. **Python 3.12** для всіх бекенд-сервісів: FastAPI + Pydantic v2 + SQLAlchemy 2 (async) + FastStream (Kafka).
3. TypeScript тільки для curation-ui.

## Обґрунтування

- Атомарні зміни контрактів: зміна події + продюсер + консюмери в одному PR, contract-тести ловлять розсинхрон одразу.
- Спільні бібліотеки (observability, connector-sdk) без публікації пакетів у registry.
- Python: ML/RAG екосистема (ембединги, матчинг) першокласна; переиспользуємо напрацювання getAttrService;
  один стек = взаємозамінність людей.
- uv: швидкий, lock-файл на workspace, нативні workspace-залежності (`libs/*` як editable).

## Наслідки

- CI має бути інкрементальним (тільки змінені пакети) — інакше повільний (вирішено `tools/changed_packages.py`).
- Дисципліна меж — через тули (import-linter, check_conventions), а не через межі репозиторіїв.
- Відмова від полірепо переглядається, якщо з'являться команди > 20 людей з незалежними циклами релізів.
