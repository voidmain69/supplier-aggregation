# ADR-0002: Гібридна взаємодія; Kafka API (Redpanda) як брокер

**Статус:** прийнято · 2026-07-11

## Контекст

Ingestion з постачальників — асинхронний за природою: rate limits (Brain: 3 req/s), великі обсяги, ретраї,
кілька незалежних споживачів одних і тих самих фактів (offer → offer-service, price-history, search).
Читання (агенти, внутрішні сервіси) вимагає передбачуваної латентності.

## Рішення

- **Події** — для всього ланцюга ingestion → каталог → офери → історія → індексація (facts, pub/sub).
- **Синхронний REST** — для читання (запити агентів і сервісів), без event sourcing на read path.
- Брокер — **Kafka API**: у dev і на старті — **Redpanda** (один бінарник, без ZooKeeper/JVM), у проді —
  Redpanda або managed Kafka без зміни коду (aiokafka/FastStream сумісні).

## Альтернативи

- *RabbitMQ*: слабші гарантії порядку по ключу, немає реплею по offset'ах — реплей нам критичний.
- *NATS JetStream*: легший, але слабша екосистема тулінгу/моніторингу і менш стандартний для найму.
- *Повний sync (без брокера)*: зв'язує конектори з усіма споживачами, ламається на rate limits і backpressure.
- *Event sourcing як основне сховище*: overkill; стан живе в PostgreSQL, події — транспорт фактів + історія цін.

## Наслідки

- Обов'язкові патерни: transactional outbox, ідемпотентні консюмери, DLQ (див. standards/events.md).
- Kafka не є довгостроковим сховищем (retention 14д) — довга пам'ять у БД і S3.
