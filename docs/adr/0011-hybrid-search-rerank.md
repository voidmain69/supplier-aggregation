# ADR-0011: Гібридний пошук — RRF-злиття лексики та семантики + cross-encoder rerank

**Статус:** прийнято · 2026-07-13

## Контекст

`search-service` ([ADR-0009](0009-search-service.md)) має два незалежні режими: лексику (token-AND) і
семантику (pgvector cosine). Кожен окремо має вади: лексика не розуміє змісту й синонімів, семантика
програє на точних кодах/артикулах і назвах. Їхні оцінки — на непорівнянних шкалах, тож просто змішати
списки не можна. Reranker-модель (`BAAI/bge-reranker-v2-m3`) уже доступна на GPU-ноді через TEI (`/rerank`),
поряд з ембедером bge-m3 ([[gpu-node-ml-stack]], PR #45).

## Рішення

Додаємо один ендпоінт `POST /v1/search/hybrid` — конвеєр retrieve → fuse → rerank:

- **Retrieve**: лексичний пул (`lexical_candidates`) і семантичний пул (`semantic_search`), по `pool`
  кандидатів кожен.
- **Fuse (RRF)**: `reciprocal_rank_fusion` — чиста domain-функція, злиття за позиціями
  (`score = Σ 1/(k+rank)`, `k=60`), **без нормалізації оцінок**; узгодженість двох ретріверів піднімає товар.
- **Rerank**: cross-encoder переоцінює пари (запит, документ) спільно й дає різку релевантність. `Reranker` —
  domain-протокол (шов), реалізація `TeiReranker` (adapter, `/rerank`) вмикається `SEARCH_RERANKER_URL`;
  дефолт **`NoopReranker`** зберігає RRF-порядок, тож пошук працює й **без GPU** (CI/тести — офлайн).

Той самий патерн шва, що й ембедер: протокол у `domain/`, HTTP-клієнт у `adapters/`, вибір реалізації —
через налаштування, офлайн-дефолт тримає тести зеленими без зовнішніх сервісів.

## Альтернативи

- *Ваговане злиття score-ів (α·lex + β·sem)* — вимагає калібрування несумісних шкал і крихке; RRF безпарамет-
  ричний і робастний.
- *Rerank без злиття (лише семантичний пул)* — втрачає точні лексичні збіги, яких немає у top-N ембедингу.
- *Rerank усього індексу* — cross-encoder дорогий; тому переоцінюємо лише злитий пул кандидатів.

## Наслідки

- Гібрид дорожчий (два retrieval + мережевий rerank) — окремий ендпоінт із `cost_class: expensive`, а не
  заміна лексичного/семантичного; клієнт обирає режим свідомо.
- Якість rerank залежить від зовнішнього TEI; недоступність деградує до RRF-порядку (`NoopReranker`), а не
  до помилки на happy-path (реальний клієнт пропагує 5xx як помилку — це усвідомлений вибір для явного сигналу).
- **Splade-sparse (`:8082`) доданий третім ретрівером** у той самий RRF (`SparseEmbedder`-шов →
  `TeiSparseEmbedder`, колонка `sparsevec` + HNSW `sparsevec_ip_ops`), опційно через
  `SEARCH_SPARSE_EMBEDDER_URL`; не налаштовано — sparse-ретрів просто вимкнено. Це підтверджує тезу:
  нові ретрівери додаються у fusion без зміни архітектури.
