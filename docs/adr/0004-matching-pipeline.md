# ADR-0004: Пайплайн матчингу — GTIN auto + RAG кандидати + людська курація

**Статус:** прийнято · 2026-07-11

## Контекст

Товари постачальників треба зводити в канонічні. Вимога бізнесу: мапінг за EAN/UPC та за RAG-ідентичністю
характеристик, **курований оператором**. Помилковий мердж двох різних товарів дорожчий за пропущений збіг
(неправильна ціна/наявність у видачі).

## Рішення

Триступеневий пайплайн (matching-service):

1. **Deterministic**: нормалізація до GTIN-14 + check digit → точний збіг → auto-link (confidence 1.0)
   без участі людини. Колізії (GTIN вказує на різні канонічні) → черга оператора з прапором конфлікту.
2. **RAG candidate generation**: ембединг нормалізованого тексту (brand + name + top-атрибути;
   нормалізація значень — підходи з getAttrService) → top-k pgvector у межах категорії →
   re-rank (brand exact, MPN fuzzy ratio, attribute overlap) → composite confidence.
3. **Human curation**: усі не-GTIN лінки отримують статус `pending_review`; тільки оператор переводить
   у `confirmed`. Рішення аудитуються і накопичуються як розмічений датасет (пороги/моделі тюнимо на ньому).

Пороги: `confidence ≥ 0.65` — показувати як кандидата; `< 0.65` — пропозиція створити новий канонічний товар.
Пороги — конфіг, не код; переглядаються по метриці precision на підтверджених рішеннях.

## Альтернативи

- *Повний авто-матчинг за схожістю*: неприйнятний ризик false merge; відкидаємо свідомо.
- *Тільки ручний*: не масштабується на 100k+ товарів; GTIN-збіги безпечні для автоматики.
- *LLM-judge замість оператора*: розглянемо як **пре-фільтр** (LLM відхиляє явні не-збіги, зменшуючи чергу),
  але фінальне слово залишається за людиною — вимога бізнесу.

## Наслідки

- Швидкість наповнення канонічного каталогу обмежена пропускною здатністю операторів —
  метрика `matching_queue_depth` і пріоритезація черги (товари з активними оферами — першими) обов'язкові.
- Датасет рішень — актив: дозволить у майбутньому підняти автопороги або натренувати кращий re-ranker.
