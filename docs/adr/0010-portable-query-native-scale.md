# ADR-0010: Portable-запит для коректності + БД-нативна структура для масштабу

**Статус:** прийнято · 2026-07-12

## Контекст

Кілька фіч спираються на можливості конкретної БД (TimescaleDB continuous aggregates, pgvector,
pg_trgm). Але юніт-тести навмисно йдуть на SQLite (без Docker, швидко), а логіка має бути коректною
незалежно від бекенду. Потрібен спосіб мати і швидкість у проді, і портабельні детерміновані тести.

## Рішення

Розділяємо **коректність** і **масштаб**:

- **Запит застосунку — портабельний**, дає правильний результат на SQLite / Postgres / Timescale однаково:
  - price-history `daily`: `GROUP BY date(ts)` + віконна функція для «last per day»;
  - search лексика: `LIKE` по `search_text`;
  - search семантика: cosine у Python як фолбек.
- **БД-нативна структура — субстрат масштабу**, ставиться міграцією і **guarded** до відповідного розширення
  (на не-Timescale/plain-PG/SQLite — no-op):
  - Timescale **continuous aggregate** `price_daily` (min/max/avg/last per день, refresh щогодини) + **compression
    policy** на сирі `price_point` чанки > 90 днів;
  - `pgvector` (cosine `<=>`, HNSW-індекс) для семантики;
  - `pg_trgm` GIN для лексики.

Нюанс реалізації: створення continuous aggregate **не можна в транзакції** → виконується в
`op.get_context().autocommit_block()` в Alembic-міграції.

## Альтернативи

- *Тестувати все на реальному Postgres/Timescale* — повільно, Docker-залежно для кожного юніт-тесту; лишаємо
  для `@integration`.
- *Читати з continuous aggregate у застосунку* — CAGG має лаг refresh (дані трохи застарілі); для транзакційного
  API портабельний запит по сирій таблиці навіть точніший. CAGG залишаємо для scale/BI (і майбутньої оптимізації,
  коли лаг прийнятний).
- *Abstraction-шар над діалектами* — надмірно; дві прості гілки (portable / native) читабельніші.

## Наслідки

- Юніт-тести залишаються швидкими й детермінованими; БД-специфіка покрита окремими `@integration` тестами на
  реальних образах (pgvector, TimescaleDB).
- Guarded-міграції безпечно застосовуються будь-де; повний прод-функціонал вмикається лише за наявності розширення.
- Ризик розходження між portable- і native-шляхом → інтеграційні тести перевіряють обидва на тих самих даних.
